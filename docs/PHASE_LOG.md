### Session 9.7 (Audio compression, 2026-07-11)
Cut the audio payload from ~21MB to ~7.2MB with ffmpeg, the last big blocker for the single-file HTML build:
- **SFX (the easy 95% win)**: the 6 sound effects shipped as uncompressed PCM WAV at ~2.1 Mbps (6.5MB total). Re-encoded to mono 96kbps MP3 → ~0.3MB total (e.g. sfx-hurricane 1941KB→88KB). Extension changed `.wav`→`.mp3`, so the 6 SFX load paths in `BootScene.js` were updated; scenes reference SFX by key, not path, so nothing else changed.
- **BGM**: the 5 tracks were already ~170-205kbps stereo MP3 (14.5MB). Re-encoded to mono 80kbps → ~7MB (roughly halved).
- **Format choice: MP3, not OGG.** OGG is more efficient at low bitrates but iOS Safari doesn't decode it, and this is a mobile-first game friends may open on iPhones. MP3 is universally supported.
- Every re-encode validated (duration preserved to <0.15s, mono, clean decode). Verified in-browser: all 11 audio keys load, bgm-overworld plays on START, and sfx-ding/splash/hurricane play at correct durations with zero console errors.
- Originals are recoverable from git history (committed at 6fe1e27 and earlier) if a track ever needs a different bitrate.

### Service worker note (from Session 9.5)
- **Service worker no longer registers on localhost** (`index.html`). Discovered live during verification: the cache-first SW was serving STALE Vite dev modules across edits, silently masking code changes (a full reload re-imports bare module URLs, which hit the runtime cache from the first load). Dev now unregisters any leftover SW + clears caches; production (gh-pages hostname) registers as before. If a dev browser ever seems to ignore edits, check Application → Service Workers first.

Notes:
- The first `RhythmBar` note arrives at `tMs = 1000` with `NOTE_TRAVEL_MS = 1500`, so its spawn offset is `-500`. The partial-travel branch handles this by computing `fraction = 500 / 1500 = 1/3`, spawning at `rightEdgeX - (1/3) * barSpan`, and tweening the remaining 1000ms to the hit zone. Without this, the first note would either be missing or misaligned.
- All `delayedCall` callbacks in the new minigames check `this.state === 'PLAY'` before touching anything. This is essential because once `win()` or `lose()` fires, the state flips away from `'PLAY'` and the result overlay runs for ~1.2s before the scene actually shuts down — any in-flight callbacks must no-op during that window or they'll touch destroyed objects and crash.
- `PipeSmoke` does NOT call `markRitualStep` itself. `BaseMinigame.win()` already does that automatically when the level config has `isRitual: true`, so calling it manually would push step 1 onto `ritualProgress` twice.
- `CokeDrinkGame` and `PipeSmoke` both use `this.input.on('pointerdown', ...)` AND `this.input.keyboard.on('keydown-SPACE', ...)`. Either input source advances the game — important for mobile-first.
- Trigger markers are re-rendered every time `OverworldScene` runs `create()`, which happens on every door transition (`scene.restart()`). Since `renderTriggerMarkers` reads `completedMinigames` fresh each time, dormant triggers stay dormant after the player leaves and re-enters the room.
- `BaseMinigame.lose()` does NOT call `markMinigameComplete`, so a failed `coke-drink` attempt leaves the trigger active and the player can re-step on it to retry. This is what makes the 5-fail hurricane test work naturally — repeated CokeDrink losses tick the failure counter without unblocking the trigger.
